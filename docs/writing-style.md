# 文本写作规范

本规范适用于一切进入仓库或被上传的文本：文档正文、代码注释、提交信息、PR 标题与描述、issue 与评论、报告与日志说明。规范由项目方于 2026-10-09 裁定。

## 1. 总则

文本采用**第三人称客观平淡陈述**。只陈述事实、现象、依据与结论，不陈述撰写者的态度。

## 2. 强制要求

| 编号 | 要求 |
|---|---|
| S1 | 不使用第一人称与第二人称：不出现「我」「我们」「你」「你们」「咱们」。改用「本编辑器」「本仓库」「项目方」「该脚本」等明确主语，或省略主语直接陈述。 |
| S2 | 不使用评价性、情绪性措辞：不出现「很棒」「遗憾」「糟糕」「完美」「值得注意」「令人惊讶」「必须强调」。判定标准是删除该措辞后信息量不变。 |
| S3 | 不使用感叹句与反问句。句末不使用「！」。 |
| S4 | 不美化结果，也不加重语气：失败写失败，未验证写未验证，未实证写未实证。 |
| S5 | 不确定的内容标注来源与状态（实测 / 推断 / 待验证 / 未验证），不写成确定结论。 |
| S6 | 结论与其依据同处一段或同处一行，避免只有结论没有依据。 |
| S7 | 既有的严重缺陷、未解问题、已知代价，保留在文档中并标注影响范围，不因修订而删除。 |

## 3. 允许的表达

* 祈使句用于规范与操作步骤（「导出统一 CRLF」「运行以下命令」），视为客观要求，不受 S1 限制。
* 「必须」「禁止」「不允许」用于硬性约束，视为客观描述，不受 S2 限制。
* 引用项目方原话时可保留原措辞，需标注为引用。

## 4. 改写示例

| 不宜 | 宜 |
|---|---|
| 我们实测发现游戏能正常加载。 | 实测：游戏可正常加载该文件。 |
| 我认为这里应该用 CRLF。 | 约定：导出统一 CRLF（依据 D3）。 |
| 这个结果很棒，说明方案可行。 | 该结果支持方案可行，依据见 §3.2。 |
| 注意！这里有个坑！ | 该处存在已知缺陷：…（影响范围：…）。 |
| 应该是 7 档吧。 | 样本中 11/12 个国家带 7 档 `<ranks>`；缺档行为未验证。 |
| 我们没实证 PC 侧根名。 | PC 侧根名未从二进制实证（§5）。 |

## 5. 适用范围外

* 面向最终用户的安装包内文档，可另行裁决措辞基调。
* 引用第三方原文（许可证、第三方声明）保持原样，不改写。
